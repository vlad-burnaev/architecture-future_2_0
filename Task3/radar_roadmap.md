# Технический радар и роадмап изменений

## Технический радар

Четыре зоны: Adopt — использовать сейчас, Trial — проверяем в пилоте, Assess — изучаем, Hold — не развиваем.

| Технология / методология | Зона | Поддерживаемые бизнес-сценарии |
|--------------------------|------|-------------------------------|
| Cloud-native lakehouse (например, Databricks / Spark + object storage) | Adopt | Горизонтальное масштабирование аналитики, быстрые витрины без многочасовых пайплайнов |
| Event streaming (Kafka / Confluent) | Adopt | Асинхронная интеграция доменов без расширения логики в DWH; онлайн-потоки финтех и ИИ |
| IAM / ABAC (например, Keycloak + OPA) | Adopt | Разграничение доступа к медицинским, финансовым и операционным данным; соответствие регуляторике |
| Data Mesh (доменное владение данными, контракты публикации) | Adopt | Независимый выпуск финтех- и ИИ-функций; подключение партнёров без переделки DWH |
| Semantic layer / метрический каталог (например, dbt + DataHub) | Adopt | Портал самообслуживания: воспроизводимые метрики и lineage для всех направлений |
| Self-service BI (например, Apache Superset / Metabase) | Adopt | Портал самообслуживания: конструктор отчётов для бизнес-пользователей |
| Infrastructure as Code — Terraform | Adopt | Воспроизводимое и масштабируемое развёртывание облачных сред доменов |
| API Gateway + контракты (OpenAPI / AsyncAPI) | Adopt | Контролируемые интеграции с партнёрами, финтехом и ИИ без прямого доступа к DWH |
| Облачный managed SQL / OLAP (например, ClickHouse Cloud / BigQuery) | Trial | Ускорение аналитических запросов для управленческой отчётности |
| MLOps платформа (например, MLflow + Feast) | Trial | Управляемый жизненный цикл ИИ-моделей; точечный доступ к медданным через feature store |
| Data contracts (автоматическая валидация схем) | Trial | Надёжность потоков между доменами при подключении новых партнёров |
| Streaming SQL (Flink / Spark Structured Streaming) | Assess | Онлайн-агрегаты для финтех-аналитики и мониторинга качества медсервисов |
| Confidential computing / шифрование на уровне данных | Assess | Соответствие регуляторике при работе с медицинскими данными в облаке |
| Microsoft SQL Server 2008 (DWH легаси) | Hold | Только исторические срезы в lakehouse; новую логику не добавляем |
| Apache Camel ESB (легаси) | Hold | Только существующие маршруты до завершения миграции на шину событий |
| Power Builder (клиентский интерфейс) | Hold | Замена в рамках домена клиники; новые функции не разрабатываем |

## Роадмап

### Этап 0 — Фундамент (месяц 1–2)

Цель: сформировать архитектурное решение и запустить базовую инфраструктуру платформы.

- Зафиксировать доменные границы и контракты публикации данных (Data Mesh).
- Развернуть облачную среду: object storage, базовый lakehouse, шину событий, IAM.
- Настроить Terraform-конфигурацию для воспроизводимого развёртывания сред.
- Определить политики доступа: медицинские данные не попадают в общую витрину.

Ответственные: архитектурная команда, DevOps / Platform Engineering, ИБ.
Ресурсы: облачный провайдер, Terraform, Kafka, IAM-решение.
Ожидаемый результат: согласованная архитектура, работающий скелет платформы, задокументированные контракты доменов.

### Этап 1 — Первые потоки и пилот витрины (месяц 2–4)

Цель: подключить первые домены к шине, запустить пилот портала самообслуживания.

- Подключить финтех-домен к шине событий (Kafka): финансовые события без логики в DWH.
- Настроить первый пайплайн DWH → lakehouse для исторических срезов.
- Развернуть dbt + DataHub: первые витрины и семантический каталог.
- Запустить пилот self-service BI (Superset / Metabase) для одного бизнес-направления.
- Параллельно: ESB продолжает работать без изменений.

Ответственные: команда финтех-домена, платформенная команда, аналитики.
Ресурсы: инженеры данных, dbt, DataHub, BI-инструмент.
Ожидаемый результат: первые отчёты через новую платформу, сокращение времени формирования с часов до минут на пилотном наборе.

### Этап 2 — Расширение доменов и портал (месяц 4–8)

Цель: подключить ИИ-домен и домен клиники, открыть портал для бизнес-пользователей.

- Подключить ИИ-домен к шине: контролируемые API, MLOps-пайплайн через feature store.
- Подключить домен клиники: события и агрегаты без медкарт и результатов исследований.
- Расширить семантический каталог: метрики по всем подключённым доменам, lineage.
- Открыть портал самообслуживания для бизнес-пользователей с ABAC.
- Начать пилот с первым внешним партнёром (фармацевтика или производитель медоборудования) через API Gateway.

Ответственные: команды ИИ-домена, клиники, платформенная команда, ИБ.
Ресурсы: MLflow, Feast, API Gateway, команды доменов.
Ожидаемый результат: портал работает для всех внутренних направлений; новый партнёр подключается без изменений в DWH.

### Этап 3 — Вывод легаси и стабилизация (месяц 8–12)

Цель: снизить зависимость от DWH и ESB, обеспечить устойчивость платформы.

- Перевести оставшиеся маршруты ESB на шину событий; вывести ESB из активной эксплуатации.
- Ограничить роль DWH: только архивные срезы, новые сценарии только через платформу.
- Внедрить data contracts с автоматической валидацией схем между доменами.
- Оценить и при необходимости запустить замену Power Builder в домене клиники.
- Провести аудит ИБ и соответствия регуляторике (медицинские и финансовые данные).

Ответственные: платформенная команда, команды доменов, ИБ, юридический отдел.
Ресурсы: инженеры миграции, инструменты data contracts, аудиторы.
Ожидаемый результат: платформа является основным каналом аналитики; легаси-системы переведены в режим архива или выведены.

## Обоснование этапов

Этап 0 критичен, потому что без зафиксированных контрактов и базовой инфраструктуры каждый следующий шаг будет переделываться. Инвестиция в IAM и политики доступа на старте снимает регуляторные риски по медицинским и финансовым данным до того, как данные начнут двигаться.

Этап 1 даёт быстрый измеримый результат для бизнеса: финтех-домен — наиболее зрелый и независимый, поэтому пилот на нём минимизирует риски. Первые витрины через dbt и DataHub сразу показывают ценность платформы и снижают давление на DWH.

Этап 2 реализует основную цель — портал самообслуживания и независимые домены. Подключение ИИ через feature store защищает медицинские данные и даёт управляемый жизненный цикл моделей. Первый партнёр через API Gateway проверяет масштабируемость архитектуры без риска для production-потоков.

Этап 3 закрывает технический долг и снижает операционные затраты на поддержку устаревшего оборудования и ПО. Вывод ESB и ограничение DWH устраняют узкое горлышко, которое тормозило time-to-market. Аудит ИБ фиксирует соответствие регуляторике как финальное условие для полноценной эксплуатации платформы.
